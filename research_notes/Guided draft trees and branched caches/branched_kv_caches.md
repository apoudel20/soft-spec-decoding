# Tree-structured, branched and persistent KV caches in LLM inference and speculative decoding

Read-depth legend. [full] = full text or HTML read this session. [abs] = abstract, snippet, slides or search summary only. [prior] = known from prior knowledge, arXiv ID not re-verified this session (treat ID as needing a check before citing). Lossless means the output distribution equals the target model's (or the output is token-identical under greedy decoding).

## Q1. Tree verification with a branched cache, and how big a tree can be before verification costs more than a decode step

### Takeaway
Tree verification with a per-round branched KV cache is mature and lossless in its main lines (SpecInfer, EAGLE-2/3, Sequoia, SpecExec, Traversal Verification). The useful tree size is set by the hardware's memory-to-compute balance. On-GPU datacenter decoding saturates at tens to a few hundred tree tokens (batch 1), while offloaded inference on consumer GPUs makes trees of 1024 to 2048 tokens nearly free.

### Cited Findings
Catalogue of tree-verification methods
- SpecInfer (Miao et al., arXiv 2305.09781). Token tree from multiple small speculative models, verified in one pass with a tree-attention mask, multi-step speculative sampling. Lossless. [prior] — [arXiv](https://arxiv.org/abs/2305.09781)
- Medusa (Cai et al., arXiv 2401.10774). Extra decoding heads on the target, fixed Cartesian-product tree verified with tree attention. Medusa-1 with typical acceptance is lossy. Exact-match rejection sampling variant is lossless. [prior] — [arXiv](https://arxiv.org/abs/2401.10774)
- EAGLE (2401.15077), EAGLE-2 (2406.16858, dynamic draft trees reranked by draft confidence as a proxy for acceptance), EAGLE-3 (2503.01840). Lossless. [prior] — [EAGLE-2](https://arxiv.org/abs/2406.16858), [EAGLE-3](https://arxiv.org/abs/2503.01840)
- Sequoia (Chen et al., arXiv 2402.12374). Dynamic programming finds optimal tree shape. Hardware-aware optimizer models verification time as a hardware-dependent function of the number of verified tokens, instead of assuming it is constant. Lossless (robust sampling-without-replacement verification). — [arXiv](https://arxiv.org/html/2402.12374v2) [abs]
- Sequoia speedups. Up to 4.04x (Llama2-7B), 3.73x (Llama2-13B), 2.27x (Vicuna-33B) on A100. Llama3-70B-Instruct offloaded to one L40 reaches 0.60 s/token, 9.5x faster than DeepSpeed-Zero-Inference. RTX 4090 offloading result of 0.56 s/token for Llama2-70B reported in a talk. Repo ships precomputed tree "growmaps" for A100 and L40. — [arXiv](https://arxiv.org/abs/2402.12374v2), [GitHub](https://github.com/infini-ai-lab/sequoia), [Together blog](https://together.ai/blog/sequoia) [abs]
- Sequoia v3 dropped "Hardware-aware" from the title, so the framing may have changed between versions. — [arXiv](https://arxiv.org/pdf/2402.12374) [abs]
- SpecExec (arXiv 2406.02532). Draft model runs a parallel shortest-path (best-first by cumulative draft log-prob) search to build a top-K tree up to depth D. The target runs once over the whole tree and fills a "cache" mapping each prefix to its next-token distribution. Sampling proceeds from that cache, and the tree is rebuilt only when the next prefix is missing. — [arXiv HTML](https://arxiv.org/html/2406.02532) [full]
- SpecExec budgets 128 to 2048 tokens. Optimal SpecExec tree on A100 with offloading is about 1024 to 2048 tokens versus 128 to 512 for SpecInfer. Llama 2-70B fp16 offloaded on A100 with budget 2048 gives about 3.1 tok/s, 18.7x, about 20.6 accepted tokens per target pass. 70B GPTQ on RTX 4090 5.66 tok/s (8.3x), RTX 3090 3.68 tok/s (10.6x), RTX 4060 3.28 tok/s (4.6x), RTX 2080 Ti 1.86 tok/s (6.1x). Without offloading (A100, Vicuna-33B with a 1.3B draft) only about 2.1 to 2.4x. Lossless, and with a fixed seed the output is identical to sequential sampling. — [arXiv HTML](https://arxiv.org/html/2406.02532) [full]
- OPT-Tree (arXiv 2406.17276). Adaptive tree construction maximizing expected acceptance length per step. Lossless. [prior] — [arXiv](https://arxiv.org/abs/2406.17276)
- DySpec (arXiv 2410.11744, ID not re-verified). Dynamic token tree grown greedily using draft probability as acceptance proxy. Lossless. [prior] — [arXiv](https://arxiv.org/abs/2410.11744)
- ProPD (arXiv 2402.13485, ID not re-verified). Early pruning of the token tree using early target layers plus dynamic tree generation tuned to runtime cost. [prior] — [arXiv](https://arxiv.org/abs/2402.13485)
- Traversal Verification (Weng et al., Lenovo, arXiv 2505.12398, NeurIPS 2025). Verifies bottom-up, a parent is checked only after all its children are rejected, so rejected nodes do not discard their whole subtree. Proven lossless and optimal for a single chain. Gains 2.2% to 5.7% in mean acceptance length, larger expected for deeper and larger trees. — [arXiv](https://arxiv.org/html/2505.12398v2), [NeurIPS](https://neurips.cc/virtual/2025/poster/119595) [abs]
- Dynamic Delayed Tree Expansion (arXiv 2602.16994) compares tree verifiers and reports Traversal Verification beats OT-based methods, but that a neural selector lets OT methods such as SpecInfer win in some settings. — [arXiv](https://arxiv.org/html/2602.16994v1) [abs]
- Recent successors seen but not read. Block diffusion draft trees (2604.12989), CAST cost-aware trees from one-pass block drafters (2610.00321, Lee and Eo), UniVer unified multi-step/multi-draft view (2605.04543). — [2604.12989](https://arxiv.org/html/2604.12989v1), [CAST](https://arxiv.org/abs/2610.00321v2), [UniVer](https://arxiv.org/pdf/2605.04543) [abs]

Compute-bound crossover numbers
- SpecExec. Offloaded 70B models can process thousands of tokens in nearly the time of one token because PCIe transfer dominates. Beyond a threshold of hundreds to thousands of tokens (model- and GPU-dependent) forward time rises at an accelerating rate. Measured on A100, RTX 4090, 3090, 2080 Ti, no H100. Llama 2-70B fp16 offloaded on RTX 3090 takes at least 4.5 s per forward. — [arXiv HTML](https://arxiv.org/html/2406.02532) [full]
- SwiftSpec (Llama3-70B, TP=4, H800). Target time is 10.32 ms at 4 tokens, 10.39 ms at 8 and 13.25 ms at 16 (about +29%). Below 8 gives no gain because 8 is the smallest tensor-core tile dimension. — [arXiv HTML](https://arxiv.org/html/2506.11309v1) [full]
- H100 roofline ridge about 300 FLOP/byte (about 990 TFLOP/s dense BF16 versus 3.35 TB/s HBM3), so batch x (spec tokens + 1) above about 300 tokens in flight is compute-bound. A 70B bf16 decode is about 42 ms of weight traffic versus 0.14 ms of math. Blog source, not peer reviewed. — [DEV Community](https://dev.to/ji_ai/speculative-decoding-why-80-acceptance-still-loses-at-batch-64-4pd4) [abs]
- Energy-accounting study using hardware counters on H100 and H200. The number of verified tokens, not the drafter, sets the crossover. Verifying 16 tokens crosses the H200 balance point at batch 16, verifying 4 stays below it up to batch 64. DFlash-16 accepts under 3 of 16 verified tokens. A draft length tuned on one GPU does not transfer to a GPU with a different balance point. — [arXiv 2610.40287](https://arxiv.org/pdf/2610.40287) [abs]
- CAST reports measured target forward latency versus packed-token count for Qwen3-8B and Qwen3-4B at batch 1 bf16 on H100 SXM and H100 NVL (Tables 5 and 6), with latency rising only modestly. Exact values not extracted (PDF unreadable to the fetch tool). — [arXiv 2610.00321](https://arxiv.org/abs/2610.00321v2) [abs]

### Inferences
- Rough rule for batch 1, on-GPU, dense model in bf16. Tree size up to roughly the ridge point (about 300 tokens on H100, by roofline) stays near one decode step in GEMM cost. In practice attention over a long prefix, kernel tiling (multiples of 8/16/64) and launch overhead make the measured knee lower, often 32 to 128 tokens for 7B to 70B models. This is consistent with SwiftSpec's +29% at 16 tokens with TP=4 and with Sequoia and SpecExec choosing 64 to 128 node trees on-GPU but 1024 to 2048 when offloaded.
- RTX 4090 ridge, from memory of public specs (about 1.0 TB/s GDDR6X, about 165 TFLOP/s dense FP16 with FP16 accumulate, roughly half that with FP32 accumulate on GeForce parts), is about 80 to 165 FLOP/byte. That suggests the free tree budget on a 4090 is roughly half to a quarter of an H100's when weights are on-GPU. Unverified, needs a benchmark.
- Weight quantization (4-bit) cuts bytes per token and so lowers the free tree budget. SpecExec's optimal budget dropping to 128 to 256 for GPTQ 4-bit (versus 2048 for fp16) is consistent with this.

### Gaps
- No source found with a clean latency-versus-tree-size curve on RTX 4090 or other consumer GPUs without offloading.
- CAST tables 5 and 6 numbers not extracted.
- DySpec and ProPD speedups and hardware not read this session.

## Q2. Persistence across rounds. Keeping rejected or unexplored branches and their KV alive, reusing drafts, and drafting ahead of verification

### Takeaway
Almost every method throws away the target's KV for rejected branches after each round. Persistence exists in three weaker forms. (a) Draft-side tree KV is kept and re-rooted on the accepted path (SwiftSpec, SpecExec's prefix cache, SSD/Saguaro's outcome-keyed speculation cache). (b) Token-level structures persist without KV (Token Recycling, lookahead n-gram pools, Ouroboros phrase pool, SuffixDecoding suffix trees). (c) Pipelined runs keep per-run KV buffers (PipeInfer). I found no published method that keeps the target model's KV for rejected or unexplored branches alive across rounds so that a later landing on that branch skips target compute. A 2026 analysis indicates exact reuse of target distributions across rounds is only valid when computed on the full next-round context, which is the core obstacle.

### Cited Findings
Draft-side or target-side tree caches that survive rounds
- SpecExec. The target pass over the whole tree populates a prefix-to-distribution cache. Generation continues by sampling from cached distributions over multiple steps, and the tree is rebuilt only when the sampled prefix leaves the cache. This is the closest published analogue to "landing on an explored branch whose target outputs are already computed", but it is within one big tree, not across rounds after rejection. Lossless. — [arXiv HTML](https://arxiv.org/html/2406.02532) [full]
- SwiftSpec (Zhang et al., ByteDance/UChicago, arXiv 2506.11309). Draft and target on separate GPU groups. The draft keeps growing the tree during verification, expanding d times per round so draft and verify times match. Draft KV has a prefix region and a tree region. When the newly verified path lies in the draft tree, the subtree under the last verified token is kept and re-laid-out, the rest dropped. Hit rate of this path not reported. Models are 4-bit AWQ Llama-3-70B, Qwen2-72B, DeepSeek-Coder-33B, R1-Distill 32B/70B with small or EAGLE drafts on 8x H800. Average 1.75x over its sequential base and 2.23x over SGLang, Llama3-70B at 348 tok/s. Parallel tree generation alone gives about 1.43x to 1.50x. Paper does not formally claim losslessness, only computational equivalence to baseline. — [arXiv HTML](https://arxiv.org/html/2506.11309v1) [full]
- Speculative Speculative Decoding / Saguaro (Kumar, Dao, May, arXiv 2603.03251, ICLR 2026). While verification runs, a draft on separate hardware predicts likely verification outcomes (accepted length plus bonus token) and prepares a speculation for each in a speculation cache. Fan-out F_k uses the top draft logits at each lookahead position, allocated as a capped geometric series under budget B. Bonus token predictable with up to about 90% accuracy. Saguaro sampling downweights cached tokens in the draft distribution to push residual mass toward cached outcomes, trading acceptance for hit rate. Misses fall back to the primary speculator at batch 1, or a fast backup at large batch. Lossless. Llama-3.1-70B on 4x H100 plus a 1x H100 draft (Llama-3.2-1B). About 30% faster than the strongest SD baselines (SGLang with EAGLE-3), up to about 5x over autoregressive, about 20% over SD at larger batches. Headline numbers differ between v1 and v3. — [arXiv v3](https://arxiv.org/html/2603.03251v3) [full], [ICLR](https://iclr.cc/virtual/2026/poster/10008711) [abs]
- Understanding Target Probability Reuse (Lee et al., arXiv 2610.29210). Studies reusing the target's next-token distributions from a verification pass to choose the next round's tree. Exact reuse is guaranteed only for distributions computed over the next round's full context, keeping such a distribution can cost accepted tokens, and the loss can persist across rounds. Proposes reranking first-token branches with a separately computed target distribution, and sampling the first token before tree allocation. Both beat draft ranking when the extra target pass overlaps drafting. — [arXiv abs](https://arxiv.org/abs/2610.29210) [abs]

Token-level persistent structures (no KV kept)
- Token Recycling (Luo et al., arXiv 2408.08696, ACL 2025). Stores candidate tokens from decoding (including rejected ones) in an adjacency matrix updated every step, BFS-builds a draft tree from it, verified with tree attention. Under 2 MB extra storage, about 2x speedup across model sizes, 30% over other train-free methods. Training-free, lossless. — [arXiv](https://arxiv.org/abs/2408.08696), [ACL Anthology](https://preview.aclanthology.org/setup/2025.acl-long.338) [abs]
- SuffixDecoding (Oliaro, Jia, Campos, Qiao, arXiv 2411.04975). Model-free. Suffix tree over tokens of current and prior requests, grown across the whole generation and across requests. Up to 2.9x throughput and 3x lower latency on a proprietary text-to-SQL pipeline, up to 2.8x on Spec-Bench (v3). CMU blog reports 5.3x on AgenticSQL and 2.5x on SWE-Bench (not checked against paper). Lossless. — [arXiv](https://arxiv.org/abs/2411.04975v1), [CMU blog](https://www.cs.cmu.edu/~csd-phd-blog/2025/suffix-decoding/) [abs]
- Lookahead decoding (Fu et al., arXiv 2402.02057). Jacobi iteration branch generates n-grams into a pool that persists over the generation, verification branch checks pool hits. Lossless. [prior] — [arXiv](https://arxiv.org/abs/2402.02057)
- Ouroboros (arXiv 2402.13720). Combines SD with lookahead-style phrase generation and a candidate phrase pool reused across rounds. Described by PEARL authors as a cache pool approach. — [PEARL paper](https://arxiv.org/html/2408.11850) [abs], [Ouroboros arXiv](https://arxiv.org/abs/2402.13720) [prior]

Drafting ahead of verification (pipelined or asynchronous)
- PEARL (arXiv 2408.11850). Pre-verify the first draft token during drafting, post-verify keeps drafting during verification. Up to 3.79x over autoregressive, 1.52x over vanilla SD. Lossless. — [arXiv](https://arxiv.org/html/2408.11850v2) [abs]
- PipeInfer (Butler et al., arXiv 2407.11798, SC 2024). Continuous asynchronous speculation runs single-token inference alongside multiple speculative runs, early cancellation back-propagates a signal to flush invalidated runs mid-pipeline, and KV cache multibuffering gives each speculative run a private KV section with pipelined cache ops so runs skip tokens earlier runs already computed. 1.5x to 2.15x over pipeline-parallel speculation. Built on llama.cpp with MPI across nodes. — [arXiv v2](https://arxiv.org/html/2407.11798v2), [researchr](https://researchr.org/publication/ButlerYMJ24/references) [abs]
- AMUSD (arXiv 2410.17375, ID not re-verified). Asynchronous multi-device SD that continues drafting under an all-accepted assumption during verification. — [cited in arXiv 2609.27396](https://arxiv.org/pdf/2609.27396) [abs]
- SchemaFill (arXiv 2610.07086). Shared arena with a persistent verified region across rounds and a scratch region for unverified candidate rows. — [arXiv](https://arxiv.org/pdf/2610.07086) [abs, snippet only]

### Inferences
- The "persistent branched target KV" idea is a gap. SwiftSpec and SSD persist draft work only. SpecExec persists target outputs only within one large tree. The 2610.29210 result explains why target-side persistence is hard. A branch's target KV and distributions are only exact if computed with the exact accepted prefix, so a persistent branch is only reusable when the accepted path is literally its ancestor path. That is the same condition as SpecExec's cache hit, so the design reduces to "a SpecExec-style tree whose unverified subtrees outlive the round".
- Under that view, the value of persistence is bounded by how often the target, after the next accepted run, lands inside a previously expanded but unaccepted subtree that sits below the accepted path. SwiftSpec's re-rooting is exactly that case on the draft side, and its unreported hit rate is the key number to measure.
- SSD's outcome-keyed cache is a one-step-deep form of this idea (cache per possible verification outcome) and is lossless with a known hit-rate/acceptance trade-off, so it is the strongest baseline to compare against.

### Gaps
- No paper found that keeps target-model KV for rejected or off-path branches across rounds. Searched phrasings "tree reuse", "draft caching", "speculative KV reuse", "KV cache retained branches". Absence is not proof.
- SwiftSpec re-root hit rate, SSD cache hit rates by fan-out, and AMUSD details not obtained.
- "When Hidden States Drift: Can KV Caches Rescue Long-Range Speculative Decoding?" (arXiv 2604.26412) surfaced but was not read. — [arXiv](https://arxiv.org/html/2604.26412)

## Q3. Shared-prefix and tree-shaped caches outside speculation, and which kernels support efficient tree-masked attention on consumer GPUs

### Takeaway
Prefix-sharing caches (RadixAttention, ChunkAttention, Hydragen, FlashInfer cascade) and tree-attention kernels (DeFT, FlashInfer custom masks, SwiftSpec's custom kernel) are well developed. FlashInfer (JIT block-sparse templates with custom masks) and Triton kernels like DeFT are the portable options that can run on consumer GPUs, though I found no consumer-GPU benchmarks for them.

### Cited Findings
- FlashInfer (arXiv 2501.01005, MLSys 2025). Customizable attention template JIT-compiled to block-sparse kernels, evaluated on speculative decoding among other workloads. Tree decoding in speculative settings is named as an attention pattern it targets. — [arXiv](https://arxiv.org/html/2501.01005v2), [UW PDF](https://homes.cs.washington.edu/~arvind/papers/flashinfer.pdf) [abs]
- FlashInfer PR #2105 (Nov 2025) adds speculative decoding to the XQA decode kernel with a causal mask tensor and q_seq_len parameter. — [GitHub](https://github.com/flashinfer-ai/flashinfer/pull/2105) [abs]
- DeFT (Yao et al., arXiv 2404.00242, ICLR 2025). KV-Guided Grouping loads each shared prefix's KV once for all queries that share it, Flattened Tree KV Splitting balances work. KV IO cut 73% to 99%, up to 2.23x decode latency and 3.59x attention latency speedup on three tree workloads. Triton implementation. — [arXiv v4](https://arxiv.org/html/2404.00242v4), [ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/a6df53f082619d02b9fad64a022e5de3-Abstract-Conference.html), [Illinois record](https://experts.illinois.edu/en/publications/deft-decoding-with-flash-tree-attention-for-efficient-tree-struct/) [abs]
- SwiftSpec tree kernel. Non-square masks (draft queries attend to prefix plus tree ancestors), masks padded so fewer than 20 CUDA Graphs cover more than 1000 mask shapes, fused split-KV attention plus combine. 30% to 56% faster than FlashAttention in microbenchmarks. — [arXiv HTML](https://arxiv.org/html/2506.11309v1) [full]
- Binary Block Matrix (arXiv 2409.15097). Makes Flash Attention skip empty blocks of partially filled masks, with Medusa tree masks as a test case. — [ar5iv](https://ar5iv.labs.arxiv.org/html/2409.15097) [abs]
- LongSpec (arXiv 2502.17421). Hybrid scheme, standard Flash Attention for cached prefix keys plus a custom masked kernel only for the few speculative tokens. — [arXiv](https://arxiv.org/pdf/2502.17421) [abs]
- SGLang RadixAttention (arXiv 2312.07104). Radix tree over token sequences mapping to KV pages, LRU eviction, automatic prefix reuse across requests and branches. [prior] — [arXiv](https://arxiv.org/abs/2312.07104)
- Hydragen (arXiv 2402.05099). Splits attention into shared-prefix and unique-suffix parts and batches the prefix part across sequences as a matrix-matrix product. [prior] — [arXiv](https://arxiv.org/abs/2402.05099)
- ChunkAttention (arXiv 2402.15220). Prefix-aware KV cache organized as a prefix tree of chunks with a two-phase partitioned kernel. [prior] — [arXiv](https://arxiv.org/abs/2402.15220)
- Tree Attention (Shyam et al., Zyphra, arXiv 2408.04093). Different meaning, a tree-reduction for exact attention across many GPUs for long context, not tree-masked speculation. [prior] — [arXiv](https://arxiv.org/abs/2408.04093)

### Inferences
- For a persistent branched cache, the attention pattern is "shared accepted prefix plus a forest of branch suffixes". That is the DeFT and Hydragen and FlashInfer-cascade shape, so prefix-once loading is the right kernel property. Dense masked FlashAttention over the whole tree wastes work in proportion to tree sparsity.
- On consumer GPUs (sm_86/sm_89), Triton kernels (DeFT) and FlashInfer's non-Hopper paths are the practical choices. Hopper-specific kernels (FA3, some XQA paths) are not.

### Gaps
- No consumer-GPU benchmarks found for DeFT, FlashInfer custom-mask or cascade kernels.
- FlashInfer cascade attention docs not fetched this session.

## Q4. Memory and bandwidth cost of keeping many branches, and optimal tree budget versus hardware

### Takeaway
The best quantitative treatments of budget versus hardware are Sequoia's hardware-aware optimizer, SpecExec's offloading analysis, SSD's fan-out budget, and the 2026 energy-accounting work. None models the memory cost of keeping branch KV alive across rounds, which has to be derived.

### Cited Findings
- Sequoia selects tree size and depth per platform using measured verification time as a function of token count. Code ships per-GPU tree maps (A100, L40), and 384 is enough for all experiments except offloading. — [arXiv](https://arxiv.org/html/2402.12374v2), [GitHub](https://github.com/infini-ai-lab/sequoia) [abs]
- SpecExec shows the optimal budget is regime-dependent. 1024 to 2048 tokens when offloaded (fp16), 128 to 256 for 4-bit offloaded, and small trees on-GPU where the speedup falls to about 2.1x to 2.4x. — [arXiv HTML](https://arxiv.org/html/2406.02532) [full]
- SSD fan-out budget B typically equals how many outcomes the draft can finish before verification completes, and more draft GPUs enlarge the cache and hit rate with expected diminishing returns. — [arXiv v3](https://arxiv.org/html/2603.03251v3) [full]
- Verified-token count sets the arithmetic-intensity crossing, and a tuned draft length does not transfer across GPUs with different balance points. — [arXiv 2610.40287](https://arxiv.org/pdf/2610.40287) [abs]
- Token Recycling's persistent structure costs under 2 MB, because it stores token IDs, not KV. — [arXiv](https://arxiv.org/abs/2408.08696) [abs]
- DeFT measures that naive per-branch kernels reload shared prefix KV, and prefix-aware grouping cuts KV IO by 73% to 99%. — [Illinois record](https://experts.illinois.edu/en/publications/deft-decoding-with-flash-tree-attention-for-efficient-tree-struct/) [abs]

### Inferences
- KV per token = 2 x layers x kv_heads x head_dim x bytes. Llama-3-8B (32 layers, 8 KV heads, 128 dim, bf16) is 2 x 32 x 8 x 128 x 2 = 128 KiB per token, so a persistent 1000-node branch forest is about 125 MiB. Llama-3-70B (80 layers, 8 KV heads) is about 320 KiB per token, about 312 MiB per 1000 nodes. Storage is cheap relative to an 80 GB or 24 GB GPU. The real cost is bandwidth. Every node kept as an attention key for later queries adds reads each step unless masked out at block granularity.
- Because branch KV is only valid under its exact ancestor path, keeping it only pays when the hit probability times saved compute exceeds the extra memory traffic and the extra tree tokens in each verification pass. In the memory-bound regime (batch 1, under the ridge) the extra tree tokens are near free, which is where persistence is most likely to help. At larger batch it should be disabled, as SSD's large-batch behaviour suggests.

### Gaps
- No paper found that analyzes memory or bandwidth of keeping branch KV across rounds, or gives an optimal persistent-forest size.
- No measured hit-rate data for "target lands on a previously explored but unaccepted branch" in any paper read.
